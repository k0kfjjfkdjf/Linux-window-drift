# windrift: перенос живых окон между двумя Linux-машинами

Прототип. Программа работает на своей машине-владельце внутри xpra-сессии, а окно можно отправить на соседнюю машину хоткеем и вернуть обратно. Клиент всегда подключается напрямую к владельцу, поэтому цепочек вида «ноутбук → ПК → ноутбук» не возникает.

```
  ПК (Hyprland)                            Ноутбук (KDE)
 ┌────────────────────────┐               ┌────────────────────────┐
 │ xpra-сервер :100       │◄──── ssh ─────│ xpra-клиент (окно)     │  ← после `send`
 │  └─ firefox (X11)      │               │                        │
 │ windrift daemon :7781  │◄── TCP/JSON ─►│ windrift daemon :7781  │  ← attach + буфер
 └────────────────────────┘               └────────────────────────┘
        ▲ lan-mouse: одна мышь и клавиатура на обе машины ▲
```

## Быстрый старт

На **первой** машине:

```bash
sudo pacman -S git xpra wl-clipboard python openssh libnotify python-gobject gtk4
git clone https://github.com/k0kfjjfkdjf/Linux-window-drift.git ~/Linux-window-drift
cd ~/Linux-window-drift
install -Dm755 windrift ~/.local/bin/windrift
install -Dm644 windrift-settings.desktop ~/.local/share/applications/windrift-settings.desktop

windrift settings          # окно настроек: имя, сосед, токен → «Сохранить»
```

Затем в том же окне нажми **«Установить на соседа»**. То же самое из терминала:

```bash
windrift setup-peer user@192.168.1.20      # или ssh-алиас: windrift setup-peer pc1
windrift setup-peer pc1 --backend kde      # если у соседа другой композитор
```

`setup-peer` всё делает по SSH сам:
1. кладёт твой ssh-ключ на соседа (один раз спросит его пароль);
2. ставит там пакеты (спросит пароль `sudo`), включает `sshd`, клонирует репозиторий и ставит `windrift`;
3. генерирует ключ на соседе и добавляет его тебе, чтобы ssh работал в обе стороны;
4. пишет соседу зеркальный конфиг с тем же токеном (старый сохраняется в `config.toml.bak`);
5. проверяет ssh туда и обратно.

Останется запустить демон на обеих машинах (см. ниже) и выполнить `windrift doctor`.

- `~/.local/bin` должен быть в `PATH` (в fish: `fish_add_path ~/.local/bin`).
- Для KDE дополнительно нужен `kdotool` (AUR).
- По желанию: `gst-python` (звук из перенесённых окон), `python-cryptography` (шифрование xpra).
- Системные часы должны быть точными, иначе ssh и TLS могут сбоить: `sudo timedatectl set-ntp true`.

## Конфиг

Файл: `~/.config/windrift/config.toml`. Каждый параметр в нём подписан, так что его удобно править вручную. Создать файл со всеми настройками по умолчанию и новым токеном:

```bash
windrift init
nano ~/.config/windrift/config.toml
```

Полный пример с комментариями лежит в [`config.example.toml`](config.example.toml). Кратко:

| Секция | Параметр | Что делает |
|---|---|---|
| — | `name`, `token`, `port`, `listen` | имя машины, общий секрет, порт и адрес демона |
| — | `backend` | `hyprland` / `kde` / `sway`: как узнать активное окно |
| — | `notify` | уведомления об ошибках |
| — | `clipboard`, `clipboard_interval`, `clipboard_max_kb` | синхронизация буфера обмена |
| `[peer]` | `name`, `host`, `port`, `ssh` | сосед: имя, адрес, порт демона, ssh-адрес или алиас |
| `[xpra]` | `encoding`, `quality` | как сжимать картинку окна |
| `[xpra]` | `speaker`, `microphone` | проброс звука и микрофона |
| `[xpra]` | `display_base`, `server_args`, `attach_args` | номера дисплеев и дополнительные аргументы xpra |
| `[setup]` | `repo`, `dir`, `packages` | что и куда ставит `setup-peer` |

Пропущенные параметры берутся по умолчанию, поэтому старые конфиги продолжают работать. Окно настроек и ручная правка пишут в один и тот же файл.

## Запуск демона

Hyprland (`hyprland.conf`):
```
exec-once = windrift daemon
```

Или через systemd (переменные Wayland должны попасть в user-окружение):
```bash
install -Dm644 windrift.service ~/.config/systemd/user/windrift.service
systemctl --user enable --now windrift
```

KDE: «Параметры системы → Автозапуск → добавить `windrift daemon`».

## Хоткеи

Hyprland:
```
bind = SUPER SHIFT, Right, exec, windrift send
bind = SUPER, B, exec, windrift run firefox
bind = SUPER, T, exec, windrift run kitty
```

KDE: «Комбинации клавиш → Добавить команду → `windrift send`».

## Проверка
```bash
windrift doctor            # всё должно быть ✓
windrift run gnome-calculator
# фокус на калькулятор → SUPER+SHIFT+Right → окно уехало на соседа
# там тот же хоткей → окно вернулось (локально, без сети)
```

## Все команды

| Команда | Что делает |
|---|---|
| `windrift init [--force]` | создать конфиг со всеми настройками |
| `windrift settings` | окно настроек |
| `windrift setup-peer [ssh] [--backend X]` | установить и настроить windrift на соседе |
| `windrift run <cmd...>` | запустить программу в переносимой сессии |
| `windrift send` | отправить активное окно соседу |
| `windrift daemon` | демон: приём окон и буфер обмена |
| `windrift list` / `stop <N>` | локальные сессии / остановить сессию |
| `windrift doctor` | проверка зависимостей и связи |

## Частые вопросы

**Можно ли перенести программу, которая уже открыта?**
Нет. Переносятся только программы, запущенные через `windrift run`. Окно обычной программы принадлежит композитору напрямую, и «пересадить» его в xpra на лету нельзя, программу придётся перезапустить. Удобнее всего повесить запуск часто используемых программ на хоткеи через `windrift run`.

**Можно ли запускать через windrift игры?**
Не стоит. Внутри xpra программа рисует на виртуальный X-дисплей, а xpra копирует каждый кадр и передаёт его клиенту. Даже когда окно показывается на той же машине, получается лишняя копия кадра, задержка ввода, а 3D обычно идёт без нормального ускорения видеокартой. FPS заметно упадёт, игра может вообще не запуститься. Игры, Steam и всё, что сильно грузит видеокарту, запускай как обычно, без `windrift run`. Такие окна просто не будут переноситься.

**А на обычные программы xpra влияет?**
Почти нет. Браузер, терминал, мессенджер и редакторы работают нормально, при локальном показе xpra использует общую память без сети. Небольшая цена — свои декорации и HiDPI-масштабирование через xpra.

## План задач

### Этап 0. База (без кода)
- [ ] Поставить `lan-mouse` (AUR) на обе машины и настроить, с какой стороны стоит сосед.
- [x] ssh по ключу в обе стороны (делает `setup-peer`).
- [x] Пакеты на обеих машинах (делает `setup-peer`).

### Этап 1. Прототип
- [x] `windrift run <cmd>`: запуск программы в отдельной xpra-сессии, показ локально.
- [x] `windrift send`: отправка активного окна соседу (Hyprland, KDE через `kdotool`, sway).
- [x] Подключение всегда к владельцу, без цепочек; возврат на владельца идёт через локальный сокет.
- [x] Демон: приём окон и синхронизация текстового буфера обмена без пинг-понга.
- [x] `windrift doctor`: проверка зависимостей, ssh и связи с соседом.
- [x] Конфиг со всеми настройками, `windrift init`, окно настроек `windrift settings`.
- [x] `windrift setup-peer`: установка и настройка соседа по SSH.

### Этап 2. Надёжность
- [ ] Автовозврат: если сосед пропал (ушёл в сон, унесли ноутбук), владелец сам подключает сессию обратно локально. Опрашивать `xpra info :N` на число клиентов.
- [ ] Безопасность: демон слушает только WireGuard-интерфейс, вместо голого токена использовать HMAC с nonce или mTLS.
- [ ] Восстановление реестра после перезапуска демона, имена окон в `list`.
- [ ] Буфер обмена: картинки и прочие MIME-типы, событийный `wl-paste --watch` вместо опроса.

### Этап 3. UX
- [ ] Окно приезжает на тот же workspace и того же размера (Hyprland IPC, `hyprctl dispatch`).
- [ ] Перетаскивание через край экрана: плагин Hyprland (C++) или KWin-скрипт ловит выход окна за границу и вызывает `windrift send`.
- [ ] Уведомление и анимация при переносе.
- [ ] Список правил: какие программы всегда запускать через windrift, а какие (игры) никогда.

### Этап 4. Технологии
- [ ] Бэкенд на `wprs` вместо xpra для нативных Wayland-приложений, без принудительного X11.
- [ ] Аппаратное кодирование видео (VA-API) для тяжёлых окон.
- [ ] Звук: проверить проброс звука в xpra или сделать отдельно через PipeWire.
- [ ] PKGBUILD для AUR.

## Известные ограничения
- Программы внутри сессии работают через X11 (режим xpra), поэтому Wayland-only приложения не поддерживаются.
- Игры и тяжёлое 3D через windrift запускать не стоит (см. «Частые вопросы»).
- Программы, запущенные не через `windrift run`, перенести нельзя.
- Если машина-владелец выключится, её окна у соседа закроются. Это фундаментальное ограничение схемы.
- Защита демона рассчитана только на доверенную локальную сеть.
- `setup-peer` рассчитан на Arch (pacman) у соседа.
